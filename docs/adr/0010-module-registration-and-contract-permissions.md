# ADR-0010：模块注册与契约内权限声明

- 状态：已接受
- 日期：2026-09-27
- 决策者：平台团队
- 被替代：无

## 背景

服务进程的组合根曾直接构造领域服务、挂载 HTTP 路由并维护按 operation ID 编写的权限路由表。这使新增领域功能需要修改中心化处理器，权限声明又与 TypeSpec HTTP 契约及 Casbin 策略相互分离，易在演进中漂移。

应用须继续保持平台层不依赖领域包、TypeSpec 为 HTTP 契约唯一事实来源，并保留按组织域执行 Casbin 授权的行为。

## 决策

引入 `internal/platform/module` 的 `Module` 生命周期接口。组合根按依赖顺序初始化启用模块，模块自行构造领域服务、发布显式命名服务并挂载自己的路由。平台仅提供共享依赖、全局中间件、文档、健康检查、Web UI 与有序关停；平台服务注册表不导入领域包。

所有需要 Casbin 授权的 TypeSpec operation 使用公共 `@permission("<resource>:<action>")` 装饰器声明 `x-permission`。服务端生成器在每个 ogen API 包清理并生成后，从 OpenAPI 规范生成 `permissions_gen.go` 的 operation ID 到权限映射。模块的路由挂载依据该表调用统一的权限中间件，不再维护处理器内的手写权限表；任何通过该中间件却缺少或格式错误权限声明的 operation 一律拒绝请求，避免意外放行。

认证模块通过平台接口贡献可选主体解析中间件；其余模块不需要平台导入 `auth` 即可使用它。组织模块在认证模块之前注册，因为注册流程需要创建个人组织。

## 备选方案

### 中心化 HTTP 处理器与手写权限表

优点是初始调用路径集中。缺点是每个新领域功能都要修改平台，且权限名称会与 OpenAPI、Casbin seed 独立漂移，因此不采用。

### 从路由实现推导权限

优点是避免额外的 TypeSpec 装饰器。缺点是授权意图不是 API 契约的一部分，生成客户端和审计工具无法读取，因此不采用。

## 结果

新增功能只需实现模块并在组合根模块列表增加一项；主程序保持小于 150 行。权限映射成为生成物，`check:generated` 会检测其漂移。

在 F1 的投递分发器合入前，模块暴露 `OutboxHandlers`，平台临时聚合并分发这些处理器；重复 topic 将使启动失败。F1 会将重试与死信策略下沉为 `delivery.Dispatcher`。
