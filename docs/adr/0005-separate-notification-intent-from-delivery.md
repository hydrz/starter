# ADR-0005：分离通知意图与交付

- 状态：已接受
- 日期：2026-09-26
- 决策者：Architecture
- 被替代：无

## 背景

身份平台会发送验证、恢复、安全告警和组织邀请消息。若业务用例直接调用 SMTP，就会把用户可见的通知意图与某一个供应商、模板、重试和发送结果绑定，且在事务失败或重试时难以保证一致性。

## 决策

通知是描述业务意图、受众、优先级和偏好的应用概念；交付是按某个渠道对一份渲染内容进行的可重试传输尝试。SMTP 是首个交付渠道，不是 notification 的同义词或唯一实现。未来 SMS、Telegram、push 或 in-app 渠道可消费同一通知意图。delivery attempt 保存渠道、状态、幂等键、提供方结果和重试信息。

## 备选方案

### 直接从业务代码发送 SMTP

实现快但破坏事务边界、无法可靠重试，也锁定未来渠道，未选择。

### 以 SMTP message 为通知领域模型

把提供商格式泄露到业务领域，无法自然表达多渠道偏好，未选择。

## 结果

业务与渠道解耦，可靠性工作集中在 outbox/delivery 边界；代价是需要额外的 intent、outbox 和 attempt 模型。`SMTP_*` 配置成组可选，只有 delivery adapter 实施时才使用。

react-starter-kit 的公开工程分层是模块边界的设计影响来源；本仓库不复制其代码。
