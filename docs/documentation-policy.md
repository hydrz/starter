# 文档规范与生命周期

## 目标

文档应让读者能找到正确入口、完成任务并理解关键决策。代码能够直接表达的实现细节不重复抄写，生成内容不手工维护。

## 文档类型

| 类型 | 回答的问题 | 位置 | 更新时机 |
| --- | --- | --- | --- |
| README | 我从哪里开始？ | 仓库或子系统根目录 | 入口、依赖或常用命令变化时 |
| Development guide | 我如何完成一项开发任务？ | `docs/development/` | 工作流或工具变化时 |
| Standard | 什么是必须遵守的？ | `docs/standards/` | 规则或自动检查变化时 |
| ADR | 为什么做出这个重要决策？ | `docs/adr/` | 决策接受、替代或废弃时 |
| Runbook | 事件发生时如何诊断和恢复？ | `docs/runbooks/` | 运行方式、指标或恢复步骤变化时 |
| Reference | 精确接口是什么？ | TypeSpec、Scalar 或生成物 | 随 SSOT 自动生成 |
| Release notes | 用户需要知道哪些变化？ | Release/变更日志 | 每次发布时 |

同一事实只能有一个权威来源。其他文档使用链接，不复制会独立变化的命令、字段列表或配置全文。

## 必需元数据

新增 development guide、standard 和 runbook 时，在标题后记录：

- **状态**：Draft、Active、Deprecated 或 Superseded；
- **负责人**：团队或角色，不使用短期个人名称；
- **最后复审**：`YYYY-MM-DD`；
- **复审周期**：建议 90、180 或 365 天。

现有文档的元数据集中维护在[文档目录](documentation-catalog.md)，后续发生实质修改时迁移到文档内。ADR 使用独立的状态和日期格式，不要求周期复审。

## 生命周期

```text
Draft ──评审──> Active ──被替代──> Superseded
                    └──不再适用──> Deprecated ──清理──> 删除
```

- Draft 可以不完整，但必须明确未生效；
- Active 是团队当前执行的版本；
- Superseded 必须链接到替代文档，并保留历史上下文；
- Deprecated 应给出迁移方向和删除条件；
- 删除前检查仓库链接、外部使用者和历史审计需求。

## 写作规则

- 标题直接描述任务或决策，段落先给结论再解释原因；
- 命令必须可复制，明确工作目录、前置条件和破坏性影响；
- 示例使用虚构数据，不包含密钥、个人信息或真实生产地址；
- 使用相对链接指向仓库文件，外部链接优先权威的一手来源；
- 截图只辅助视觉说明，关键步骤必须同时用文字表达；
- 时间敏感内容注明版本或复审日期。

## 自动检查

`pnpm check:docs` 扫描根 README、贡献指南和 `docs/`：

1. 每个 Markdown 文件必须恰好有一个一级标题；
2. 仓库内的相对文件和图片链接必须存在；
3. 检查失败会列出文件与断开的目标。

自动检查不能判断内容是否正确。代码评审仍需验证命令、所有者、风险提示和实现是否一致。
