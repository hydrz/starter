# 文档规范与生命周期

## 目标

文档应让读者能找到正确入口、完成任务并理解关键决策。代码能够直接表达的实现细节不重复抄写，生成内容不手工维护。

## 文档类型

| 类型 | 回答的问题 | 存放位置与命名规则 | 对应模板 | 登记索引 | 更新时机 |
| --- | --- | --- | --- | --- | --- |
| README | 我从哪里开始？ | 仓库或子系统根目录 `README.md` | - | [文档中心](README.md) | 入口、依赖或常用命令变化时 |
| Development guide | 我如何完成一项开发任务？ | `docs/development/<name>.md` | [功能指南模板](templates/feature-guide.md) | [文档目录](documentation-catalog.md) | 工作流或工具变化时 |
| Standard | 什么是必须遵守的？ | `docs/standards/<topic>.md` | - | [规范索引](standards/README.md) | 规则或自动检查变化时 |
| ADR | 为什么做出这个重要决策？ | `docs/adr/NNNN-<title>.md` (4位序号) | [ADR 模板](templates/adr.md) | [ADR 索引](adr/README.md) | 决策接受、替代或废弃时 |
| Runbook | 事件发生时如何诊断和恢复？ | `docs/runbooks/<name>.md` | [Runbook 模板](templates/runbook.md) | [Runbook 索引](runbooks/README.md) | 运行方式、指标或恢复步骤变化时 |
| Reference | 精确接口是什么？ | TypeSpec、Scalar 或生成物 | - | 随 SSOT 自动生成 | 随代码/契约自动同步 |
| Release notes | 用户需要知道哪些变化？ | GitHub Release 描述 / `docs/releases/` | [发布说明模板](templates/release-notes.md) | [交付指南](deployment.md) | 每次发布时 |

同一事实只能有一个权威来源。其他文档使用链接，不复制会独立变化的命令、字段列表或配置全文。使用模板创建文档的完整流程参见[文档模板指南](templates/README.md)。

## 必需元数据

新增 development guide、standard 和 runbook 时，在标题后记录：

- **状态**：文档当前所处的生命周期状态，取值仅限 `Draft`、`Active`、`Deprecated`、`Superseded`（见下表说明）；
- **负责人**：团队或角色，不使用短期个人名称；
- **最后复审**：`YYYY-MM-DD`；
- **复审周期**：建议 90、180 或 365 天。

现有文档的元数据集中维护在[文档目录](documentation-catalog.md)，后续发生实质修改时迁移到文档内。ADR 使用独立的状态和日期格式，不要求周期复审。

## 状态定义与生命周期

```text
Draft ──评审确认──> Active ──被新方案替代──> Superseded
                        └──技术退役/不再适用──> Deprecated ──全库无引用──> 删除
```

文档状态必须使用以下受控词汇，严禁混用其他非标词汇：

| 状态 | 含义与效力 | 适用场景 | 必需动作与约束 |
| --- | --- | --- | --- |
| **`Draft`** | **草稿 / 评审中**<br>内容尚未最终定稿，不具备团队强制执行效力。 | 新增指南编写中、工作流重构提案评审期。 | 必须标明“未生效”，不得作为 CI 或代码评审的阻断依据。 |
| **`Active`** | **生效中 / 当前标准**<br>团队当前唯一认可并严格执行的权威版本。 | 已经过评审确认的现行规范、手册、架构蓝图与开发指南。 | 定期按复审周期核验；内容必须与实际代码和工具行为保持 100% 同构。 |
| **`Superseded`** | **已被替代**<br>曾经生效，但已有更新的文档取代其位置。保留仅作历史追溯。 | 架构演进产生新版指南（如迁移到新框架、新生成器）。 | **必须**在正文第一行提供指向新文档的超链接，说明替代原因与日期。 |
| **`Deprecated`** | **已废弃 / 待清理**<br>相关能力或流程已被淘汰，不再推荐使用，处于退役倒计时。 | 废弃工具迁移期、即将移除的旧流程。 | 必须明确标出替代建议与最终清理期限；当全库链接归零后可安全物理删除。 |

## 写作规则

- 标题直接描述任务或决策，段落先给结论再解释原因；
- 命令必须可复制，明确工作目录、前置条件和破坏性影响；
- 示例使用虚构数据，不包含密钥、个人信息或真实生产地址；
- 使用相对链接指向仓库文件，外部链接优先权威的一手来源；
- 截图只辅助视觉说明，关键步骤必须同时用文字表达；
- 时间敏感内容注明版本或复审日期。

## 自动检查

`pnpm check:docs` 扫描根 README、贡献指南和 `docs/`：

1. 每个 Markdown 文件必须恰好有一个一级标题；
2. 仓库内的相对文件和图片链接必须存在；
3. 检查失败会列出文件与断开的目标。

自动检查不能判断内容是否正确。代码评审仍需验证命令、所有者、风险提示和实现是否一致。
