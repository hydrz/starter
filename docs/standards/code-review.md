# 代码评审清单

## 作者自检

- [ ] 变更范围单一，PR 描述解释了动机、方案与风险；
- [ ] 依赖方向符合工程蓝图，没有绕过应用层泄露 transport/store 类型；
- [ ] API、migration、查询从各自 SSOT 修改，生成文件未手工编辑；
- [ ] 错误对调用者可操作，内部实现细节不会泄露；
- [ ] 新行为与失败路径有测试，相关检查已实际运行；
- [ ] 配置、日志、测试数据和截图不包含密钥或个人信息；
- [ ] 文档、示例命令和变更后的实际行为一致；
- [ ] 已考虑兼容性、并发、事务、超时和资源释放；
- [ ] 视觉变更覆盖加载、空、失败、窄屏和键盘操作；
- [ ] 必要例外已记录原因、替代控制、负责人和清理期限。

## 评审者关注点

评审者优先判断设计与风险，而不是手工代替 formatter：

1. 契约和数据是否保持向后兼容；
2. 业务不变量是否处于正确层并由数据库做最后保护；
3. 错误、日志和监控是否足以诊断且不会泄密；
4. 测试是否能在实现错误时失败，而不仅是执行代码；
5. 是否引入不必要抽象、重复状态或隐式副作用；
6. 部署、迁移和回滚/向前修复步骤是否现实可执行。

纯风格意见使用“建议”标注，不阻塞合并；违反自动化规则、数据安全、契约兼容或明确架构边界的问题必须解决后才能合并。
