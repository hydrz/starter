# Go 工程规范

## 包与依赖

- `apps/` 只负责进程装配、配置读取、生命周期和退出码；
- `internal/<feature>` 表达业务用例与领域不变量，不依赖 HTTP；
- `internal/platform` 放置 HTTP、数据库等技术适配器；
- sqlc 生成代码只存在于 `internal/store`，业务层不得直接暴露其类型；
- 接口由使用方定义，并保持满足当前用例所需的最小方法集合；
- 不为只有一个简单实现且不存在隔离价值的对象预建接口。

## 错误处理

- 错误必须被处理或显式返回，不得丢弃；
- 使用 `%w` 保留错误链，调用方通过 `errors.Is`/`errors.As` 判断语义；
- 稳定业务语义使用包级 sentinel 或具体错误类型；
- HTTP 层负责将领域错误转换为公开错误码，未知错误不得把数据库或堆栈细节返回客户端；
- 日志只在能够采取行动的边界记录一次，避免逐层重复记录同一错误。

## 并发与生命周期

- 所有可能阻塞的调用接收 `context.Context`，且 context 作为首个参数；
- goroutine 必须有明确的停止信号、所有者和错误传播路径；
- 网络服务必须配置超时并支持优雅关闭；
- 数据库连接、响应体、rows 和其他资源由创建它们的层负责关闭。

## 命名与代码形态

- 使用 `gofmt`，不手工对齐或维护替代格式；
- 包名简短、单数且表达职责，避免 `utils`、`common` 等无边界名称；
- 导出标识符只在跨包需要时出现；
- 函数优先保持单一职责；只有重复已出现且抽象能表达业务概念时才提取通用层。

## 最低验证

Go 变更至少运行 `pnpm check:go` 和 `go test ./...`。涉及并发、共享状态或基础设施适配器时还需运行 `pnpm test:race`。
