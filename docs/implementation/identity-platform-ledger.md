## A 的接口决策

- `config.Load(os.LookupEnv)` returns `config.Config` or a `*config.ValidationError`; validation messages include environment variable names only, never values.
- Current startup reads `DatabaseURL`、`Address` 和 `AutoMigrate` from this config while retaining defaults: database URL points at the local starter database, address is `:8080`, and auto migration is enabled except for exact `AUTO_MIGRATE=false`.
- Auth, OAuth (Google/GitHub), WebAuthn, SMTP, Stripe, authorization, and worker configurations are parsed but do not initialize any future service. Every optional group is disabled when entirely absent; partial groups fail with missing names. The auth group requires `AUTH_JWT_ACTIVE_KID`, `AUTH_JWT_SIGNING_PRIVATE_KEY`, `AUTH_JWT_VERIFICATION_KEYSET`, `AUTH_JWT_ISSUER`, `AUTH_JWT_ACCESS_TTL`, and `AUTH_REFRESH_TOKEN_TTL` together.
- Future issuers use `AuthConfig.SigningPrivateKey` for EdDSA and write `AuthConfig.ActiveKID` into the protected JWT `kid`; future verifiers reject absent/unknown `kid` and use only `AuthConfig.VerificationPublicKeys[kid]`. The active public key must match the signing private key; the keyset may retain prior public keys for rotation. Key material is unpadded base64url in environment variables, and config errors name variables only.
- `WorkerConfig` defaults to a one-second poll interval and batch size 50; it only enables when `WORKER_ENABLED=true`.
- Shared TypeSpec errors now cover 401, 403, 409, 412, and 429 in addition to existing 400, 404, and 503. No feature route consumes them yet.
- `compose.yaml` is intentionally unchanged because current compose only needs PostgreSQL/current app startup; optional integrations have no runtime dependency until their owners implement them.

## B 的接口决策

- New domain package `internal/auth` (not `internal/identity`, matching the overall plan) exposes `Service` with narrow `UserRepository`, `RefreshTokenRepository`, `OneTimeTokenRepository`, `APIKeyRepository`, `OutboxWriter`, and `Transactor` ports; it never leaks `internal/store` or `internal/api/authapi` types outside `internal/auth/postgres.go` and `internal/auth/handler.go`.
- `auth.Issuer`/`auth.Verifier` issue and verify only EdDSA JWTs using `config.AuthConfig.ActiveKID`/`SigningPrivateKey`/`VerificationPublicKeys`; claims are limited to `sub`, `sid`, `jti`, `iss`, `aud`, `iat`, `nbf`, `exp`, `typ=access`. No role/org/entitlement claim is added, per the frozen contract.
- Passwords use Argon2id PHC hashes (`auth.HashPassword`/`VerifyPassword`) with constant-time comparison and a fixed dummy-hash comparison (`VerifyPasswordOrDummy`) for unknown emails, so sign-in timing does not reveal account existence.
- Refresh, verification, and API-key secrets are never stored raw: `auth.SecretDigester` stores only a versioned HMAC-SHA256 digest, keyed by a dedicated `AuthConfig.SecretDigestPepper` (environment variable `AUTH_SECRET_PEPPER`, part of the existing all-or-none auth group) rather than being derived from the JWT signing key, so rotating the JWT signing key never silently invalidates stored refresh/reset/API-key digests. Digests are recorded in `db/migrations/00002_create_identity_and_delivery.sql` (`refresh_sessions.token_digest`, `one_time_tokens.token_digest`, `api_keys.secret_digest`). Refresh rotation and one-time-token consumption use single conditional `UPDATE ... WHERE ... RETURNING` statements (`db/queries/auth.sql`: `ConsumeRefreshSession`, `ConsumeOneTimeToken`) so there is no check-then-update race; a refresh token that cannot be consumed (already replaced/revoked/expired) but is still a known digest is treated as reuse and revokes its whole family via `RevokeRefreshFamily`.
- Sign-up writes the new `users` row and its first `notification_intents`/`outbox_events` rows (topic `auth.verification_requested`) inside one `database.PgxTransactor` transaction; password reset confirmation revokes every refresh family for the account inside the same transaction as the password update. Auth never calls SMTP inline; it only writes outbox rows for a future delivery worker (workstream D) to claim.
- API keys (`api_keys` table) carry a nullable `organization_id` column with no foreign key yet, so workstream C can add organization scoping later without a forward-only migration that blocks on a not-yet-existing organizations table; the raw key is only returned once, at `CreateAPIKey` time.
- The refresh token itself is delivered only via an HttpOnly/Secure/SameSite=Lax cookie scoped to `Path=/api/auth` (`auth.RefreshCookieName`/`RefreshCookiePath`); no browser storage guidance is implied beyond keeping the access token in memory, which remains a caller (F) concern.
- Public HTTP surface lives at `packages/contracts/features/auth/{models,routes,auth}.tsp`, imported from `main.tsp`, compiled only through `pnpm generate`; all operations are mounted at `/api/auth/*` (`internal/platform/httpserver/handler.go`), reusing A's common `ApiError`/`UnauthorizedResponse`/`ConflictResponse`/`TooManyRequestsResponse` models.
- `httpserver.NewHandler` gained a third, optional `*auth.Service` parameter; when nil (auth disabled), no `/api/auth/*` route is registered and existing health/docs/announcements behavior is unchanged. `auth.AuthenticationMiddleware` only resolves an optional bearer principal into context for the auth handler's own operations (e.g. `GetCurrentIdentity`, session/API-key management); it does not protect any other route, per the integration gate reserving global authorization middleware for workstream C.
- `apps/server/main.go` keeps A's config-driven `cfg.Address`/`cfg.DatabaseURL`/`cfg.AutoMigrate` startup logic unchanged and adds only identity-service wiring: when `cfg.Auth.Enabled`, it builds `auth.Service` via `buildIdentityService` and passes it into `apphttp.NewHandler`. `config.AuthConfig` gained one additional required field, `SecretDigestPepper` (env `AUTH_SECRET_PEPPER`), joining the existing all-or-none auth group; it is independent, high-entropy secret material unrelated to `SigningPrivateKey`, used only to key `auth.SecretDigester`.

## C 的接口决策

- Database schema migration `db/migrations/00003_create_organizations_and_authorization.sql` creates `organizations`, `organization_memberships`, `organization_invitations`, and `casbin_rules` tables with forward-only DDL, seeds the default role policies (`owner`, `admin`, `member`, `viewer`), scopes `announcements` by `organization_id`, and adds the foreign key from `api_keys.organization_id` to `organizations(id)`.
- New domain package `internal/authorization` implements Casbin v2 enforcer initialization with standard domain RBAC model (`g = _, _, _`), `DatabaseAdapter` backed by `internal/store` queries and in-memory `MemoryAdapter` for hermetic testing. It provides a narrow `Authorizer` service interface (`Authorize(ctx, sub, dom, obj, act) (bool, error)`) and Chi middleware `RequirePermission(enforcer, resource, action)` that evaluates `sub` from the authenticated context, `dom` from URL parameter `organizationId`, verifies organization membership, and executes Casbin enforcement.
- New domain package `internal/organization` implements `Service` with narrow ports over `Repository` and `database.Transactor`. It supports organization CRUD, atomic personal workspace provisioning on signup via `auth.PersonalOrgCreator`, membership management, invitation lifecycle with HMAC-SHA256 token digests, role updates, and last-owner protection.
- `internal/auth.Service.SignUp` accepts optional `PersonalOrgCreator` in its dependencies, creating the new user's personal organization atomically within the same database transaction.
- Resource tenant scoping: `internal/announcement` repository, service, and HTTP handler are updated to take `organizationID uuid.UUID` on all operations.
- TypeSpec contracts: added `packages/contracts/features/organizations/{models.tsp, routes.tsp, organizations.tsp}` and scoped announcements under `/api/organizations/{organizationId}/announcements` in `features/announcements/routes.tsp`. Top-level contract `packages/contracts/main.tsp` imports both.
- Server wiring: `internal/platform/httpserver.NewHandler` accepts `orgs *organization.Service` and `authorizer authorization.PermissionEnforcer`, exposing `/api/organizations` and protecting all tenant-scoped routes under `/api/organizations/{organizationId}/*` and `/api/organizations/{organizationId}/announcements/*` via `RequirePermission`. `apps/server/main.go` instantiates the database adapter, Casbin enforcer, authorization service, organization service, and passes the personal org provisioner to `buildIdentityService`.

## D 的接口决策

- New package `internal/delivery` provides the outbox worker (`delivery.Worker`), delivery channel abstraction (`delivery.Channel`, `delivery.Message`), standard SMTP adapter (`delivery.SMTPChannel`, `delivery.NoopChannel`), and dual-mode template rendering engine (`delivery.TemplateRenderer`).
- Outbox processor (`delivery.Worker`) periodically claims batches of due events (`available_at <= now() AND processed_at IS NULL AND (claimed_at IS NULL OR claimed_at < now() - timeout)`) using PostgreSQL `SELECT ... FOR UPDATE SKIP LOCKED` (`ClaimOutboxEvents`), parameterized by `config.WorkerConfig.BatchSize` (default 50), `config.WorkerConfig.PollInterval` (default 1s), and `ClaimTimeout` (default 5m). Shutdown is gracefully coordinated via `context.Context`.
- SMTP channel (`delivery.SMTPChannel`) supports standard SMTP, Resend, and Cloudflare Email Routing with proper TLS/STARTTLS handling (direct TLS on port 465, STARTTLS upgrade on port 587, PLAIN authentication, and RFC 2822/5322 MIME `multipart/alternative` formatting with UTF-8 text and HTML). `delivery.NoopChannel` allows development and testing without SMTP credentials.
- Dual-mode email templates for `auth.verification_requested` and `auth.password_reset_requested` use standard library `html/template` and `text/template` embedded via `embed.FS` (`internal/delivery/templates/`).
- Domain package `internal/notification` provides `Service` implementing `delivery.Handler`. When `auth.verification_requested` or `auth.password_reset_requested` outbox events are claimed, it translates them into `notification_intents`, renders dual-mode templates, persists `delivery_messages` with channel `smtp` and unique idempotency key (`outbox:<event-id>:smtp`), and records `delivery_attempts`.
- On delivery success, records attempt status `sent` with provider response and marks outbox event processed (`MarkOutboxEventProcessed`). On delivery failure, records attempt status `failed` with error message, computes exponential backoff (`CalculateBackoff`), and schedules retry (`RetryOutboxEvent`).
- `apps/server/main.go` wires `delivery.Worker` in the background when `cfg.Worker.Enabled || cfg.SMTP.Enabled`, stopping cleanly on SIGTERM/SIGINT within the shutdown timeout.

## E 的接口决策

- New package `internal/billing` is the ONLY package permitted to import the Stripe Go SDK (`github.com/stripe/stripe-go/v81`). Its public surface never leaks `internal/store`/ogen or Stripe SDK types: `billing.Service` exposes domain types (`BillingAccount`, `CheckoutSession`, `Subscription`, `OneTimePurchase`, `Entitlement`, `Summary`) and a narrow `EntitlementReader` interface (`HasEntitlement(ctx, organizationID, featureKey) (bool, error)`) that future authorization/product checks can depend on without importing Stripe or `internal/billing` internals. Repository/gateway ports (`BillingAccountRepository`, `CheckoutSessionRepository`, `SubscriptionRepository`, `OneTimePurchaseRepository`, `WebhookEventRepository`, `EntitlementRepository`, `StripeGateway`, `Transactor`, `OutboxWriter`, `Clock`) mirror `internal/auth`'s narrow-port style; `StripeGateway` is the only interface a production type (`billing.LiveGateway`, in `stripe.go`) implements with the Stripe SDK, so `service.go`/`postgres.go`/`handler.go` stay SDK-free and every port has an in-memory fake for hermetic unit tests (no PostgreSQL/Stripe network required to run `go test ./internal/billing`).
- Database schema migration `db/migrations/00004_create_billing.sql` creates `billing_accounts` (one per organization, `organization_id` UNIQUE FK), `checkout_sessions`, `subscriptions`, `one_time_purchases`, `stripe_webhook_events` (`stripe_event_id` UNIQUE — the idempotency key), and `entitlements` (organization + feature_key + **source** ∈ {`subscription`,`one_time`}, UNIQUE on all three), plus seeds Casbin policies for a new `billing` resource (`read`/`checkout`/`portal` actions; owner/admin get all three, member/viewer get `read` only). All monetary amounts are `bigint` minor units plus an ISO currency `text` column, never a float. `db/queries/billing.sql` adds `CreateBillingAccount` (insert-or-get), `Get*ByOrganization`/`Get*ByStripeCustomerID`, `CreateCheckoutSession`/`GetCheckoutSessionByStripeID`/`UpdateCheckoutSessionStatus`, `UpsertSubscription` (a single `INSERT ... ON CONFLICT ... DO UPDATE ... WHERE subscriptions.last_event_created_at IS NULL OR < EXCLUDED.last_event_created_at` — the monotonic out-of-order guard; a rejected/stale event returns zero rows, which the repository treats as a no-op, not an error), `InsertOneTimePurchase` (`ON CONFLICT (stripe_checkout_session_id) DO NOTHING`), `InsertWebhookEvent` (`ON CONFLICT (stripe_event_id) DO NOTHING RETURNING ...` — the single-statement, constraint-based idempotency check the task required, not check-then-insert), and `UpsertEntitlement`/`HasEntitlement`/`ListEntitlementsForOrganization`.
- Entitlements are modeled per `(organization_id, feature_key, source)` rather than per `(organization_id, feature_key)` specifically so that cancelling a subscription only disables its own `source='subscription'` row; a separate `source='one_time'` row granting the same `feature_key` is never touched by that update, and `HasEntitlement`/`EntitlementReader.HasEntitlement` return true if *any* enabled, unexpired row exists for that org+feature — this is covered by `TestHandleWebhook_CancellingSubscriptionNeverRevokesOneTimePurchase` in `internal/billing/webhook_test.go`.
- TypeSpec contract: `packages/contracts/features/billing/{models.tsp,routes.tsp,billing.tsp}`, imported from `main.tsp`, mounted at `/api/organizations/{organizationId}/billing/*` (mirroring `features/organizations`): `GET /summary` (current subscription/entitlement state), `POST /checkout-sessions` (body is `CreateCheckoutSessionInput { priceKey: string }` — **only** a server-controlled catalog key; never a client-supplied Stripe price/customer/subscription ID, amount, or success/cancel URL), and `POST /portal-sessions` (no body — the return URL is server-configured). All three reuse `common/responses.tsp`'s `ApiError`-based `UnauthorizedResponse`/`ForbiddenResponse`/`NotFoundResponse`/`BadRequestResponse` exactly like `features/auth`/`features/organizations`.
- Server-controlled price catalog: `internal/billing.Catalog` (`catalog.go`) maps a price key to `{StripePriceID, FeatureKey, Mode}`; `Service.CreateCheckoutSession` looks the client's `priceKey` up in this catalog and returns `ErrUnknownPriceKey` (400) for anything not in it — the client can never reach a Stripe price ID, amount, or customer ID directly. `apps/server/main.go`'s `buildBillingService` loads the catalog from an optional `BILLING_PRICE_CATALOG` JSON env var (`billing.ParseCatalogJSON`) and reads `BILLING_SUCCESS_URL`/`BILLING_CANCEL_URL`/`BILLING_PORTAL_RETURN_URL` (with same-origin defaults) directly via `os.Getenv`, entirely outside `config.StripeConfig` — `internal/platform/config.StripeConfig`'s shape (`Enabled`, `SecretKey`, `WebhookSecret`, `PublishableKey`) is unchanged, only consumed.
- Webhook endpoint: `billing.WebhookHTTPHandler` (`webhookhttp.go`) is a raw `http.Handler`, mounted directly at `/api/billing/webhooks/stripe` in `internal/platform/httpserver.NewHandler` — **not** through the TypeSpec/ogen JSON router — so it controls, in order, a 1 MiB `http.MaxBytesReader` body-size limit, then `Stripe-Signature` HMAC verification via stripe-go's `webhook.ConstructEvent` (`webhook.go`), both strictly before any event-type/JSON-field parsing. `Service.HandleWebhook` then looks up the Stripe event ID via `WebhookEventRepository.Insert`'s `ON CONFLICT DO NOTHING` inside one `database`-style `Transactor.WithinTransaction` call that also applies the subscription/entitlement projection, so recording the event and updating projections are atomic (all-or-nothing) rather than two separate steps; an already-recorded event ID returns 200 immediately as a no-op. Any non-signature persistence failure inside that transaction is returned as a Go `error` and mapped by `WebhookHTTPHandler` to `500` (never swallowed as `2xx`, so Stripe retries); a bad/missing signature maps to `400`; body over the 1 MiB limit maps to `413`. Checkout success/cancel are plain browser redirect URLs configured server-side (`SuccessURL`/`CancelURL`) with no server route of their own — nothing reads them to grant an entitlement; only `HandleWebhook`'s `checkout.session.completed`/`customer.subscription.*` handling ever calls `EntitlementRepository.Upsert`.
- Wiring: `apps/server/main.go` builds `billing.Service` via `buildBillingService` when `cfg.Stripe.Enabled`, following the exact nil-safe optional-service pattern used for `identityService`/`orgService`, and passes it as a new final parameter to `apphttp.NewHandler`. `internal/platform/httpserver.NewHandler` gained a `*billing.Service` parameter; when nil, neither the `/api/organizations/{organizationId}/billing/*` routes nor the webhook route are registered. Every billing route enforces, in order: (1) `identity.AuthenticationMiddleware` (authenticate), (2) `authorization.RequirePermission(authorizer, "billing", <read|checkout|portal>)` (organization membership + Casbin permission — identical to how `organizations`/`announcements` routes are protected), and (3) billing-account ownership: `billing.HTTPHandler` and `Service` **only ever** resolve a billing account through the URL's `organizationId` (`GetByOrganization`) — they never accept or trust a client-supplied billing-account/customer/subscription ID — so cross-organization access is structurally impossible, not just policy-checked; covered by `TestBillingAccountIsolationAcrossOrganizations` (`internal/billing`) and `TestBillingRouting` (`internal/platform/httpserver`).
- Billing never calls a delivery channel directly (ADR-0005/0007): `billing.PostgresOutboxWriter` (reusing the same `outbox_events` table/pattern as `internal/auth`) writes a `billing.subscription_updated`/`billing.one_time_purchase_completed` row inside the same webhook-processing transaction when `Dependencies.Outbox` is configured; `Outbox` is optional so billing still functions (summary/checkout/portal/webhook processing) with notifications wired up later by workstream D.
- Security invariants and their tests, all in `internal/billing/{service_test.go,webhook_test.go,webhookhttp_test.go}` plus `internal/platform/httpserver/handler_test.go`'s `TestBillingRouting`, run against in-memory fakes (no PostgreSQL/Stripe network): (1) duplicate/out-of-order webhooks never double-grant/wrongly-revoke/drop entitlements — `TestHandleWebhook_DuplicateEventIsNoOp`, `TestHandleWebhook_OutOfOrderSubscriptionEventDoesNotRegress`; (2) cancelling a subscription never revokes a one-time purchase's entitlement — `TestHandleWebhook_CancellingSubscriptionNeverRevokesOneTimePurchase`; (3) cross-organization billing access is rejected — `TestBillingAccountIsolationAcrossOrganizations`, `TestBillingRouting` (401/403, and a billing account is structurally unreachable via another organization's ID); (4) raw webhook payloads/Stripe secrets/card data are never logged or persisted — `stripe_webhook_events` only stores `stripe_event_id`/`event_type`/`event_created_at`/`received_at`, and no code path logs the raw request body or `cfg.Stripe.SecretKey`; (5) checkout-success redirects/status codes are never proof of payment — there is no HTTP route reading the browser's checkout-return query string, and `CreateCheckoutSession`/`CreatePortalSession` never call `EntitlementRepository.Upsert` themselves, only `HandleWebhook` does, covered indirectly by every webhook test asserting entitlements are unset until a verified event arrives.

## F 的接口决策

- **F 复用而非并行实现会话签发**：`internal/auth/otp.go`（Email OTP）、`internal/auth/totp.go`（TOTP 因子/恢复码/MFA challenge）、`internal/auth/oauth.go`（OAuth 账户/授权 state）、`internal/auth/oauth_client.go`（`golang.org/x/oauth2` 封装）、`internal/auth/webauthn.go`（`github.com/go-webauthn/webauthn` 封装）都是 `package auth` 的新增文件，全部是 `auth.Service` 的新方法，没有新建 `internal/mfa`/`internal/oauth` 包。每一个"完成登录"的路径——`VerifyEmailOTP`、`VerifyMFAChallenge`、`CompleteOAuthSignIn`、`FinishWebAuthnAuthentication`——在成功时都会调用 `service.refreshTokens.CreateFamily` 后紧接 `service.issueSessionTokens`（`internal/auth/service.go:393`，未导出），这是本仓库中唯一签发 JWT access token 与 opaque refresh token 的位置；`PasswordSignIn`（既有方法）本身被就地扩展，新增了对 `checkMFARequired` 的调用，没有引入第二条签发路径。仓库中对 `issueSessionTokens` 的全部调用点均位于 `internal/auth/service.go`、`internal/auth/otp.go`、`internal/auth/totp.go`、`internal/auth/oauth.go`、`internal/auth/webauthn.go`。
- **新增端口（ports），narrow、可 fake**：`EmailOTPRepository`、`TOTPFactorRepository`、`TOTPRecoveryCodeRepository`、`MFAChallengeRepository`、`OAuthAccountRepository`、`OAuthStateRepository`、`WebAuthnCredentialRepository`、`WebAuthnChallengeRepository`。全部在 `auth.Dependencies`/`auth.Service` 上是**可选**字段（nil-safe）：未注入时对应功能直接返回 `ErrInvalidInput`/无操作，因此既有 `internal/auth/service_test.go` 的全部 32+ 个测试无需任何改动即可继续通过（已验证）。
- **数据库**：新迁移 `db/migrations/00005_create_mfa_oauth_webauthn.sql`（forward-only，未改动 00001–00004）新增 `email_otp_challenges`、`totp_factors`、`totp_recovery_codes`、`mfa_challenges`、`oauth_accounts`（`UNIQUE (provider, provider_subject)`，账户解析的唯一身份键）、`oauth_authorization_states`（`state`/`nonce`/PKCE `code_verifier`，`intent` ∈ {`sign_in`,`link`}，`link` 时必须携带 `linking_user_id`）、`webauthn_credentials`、`webauthn_challenges`（持久化完整 `webauthn.SessionData` JSON，而不仅是原始 challenge 字节）。`db/queries/{otp,totp,oauth,webauthn}.sql` 为每一种单次性资源提供单语句原子 consume：`ConsumeEmailOTPChallengeByID`、`ConsumeMFAChallenge`、`ConsumeTOTPRecoveryCode`、`ConsumeOAuthAuthorizationState`、`ConsumeWebAuthnChallenge`，均为 `UPDATE ... WHERE ... AND consumed_at IS NULL ... RETURNING`，与 B 的 `ConsumeRefreshSession`/`ConsumeOneTimeToken` 同一模式。Email OTP 的暴力枚举防护拆成两步：`IncrementEmailOTPAttempt`（原子递增、`attempt_count < max_attempts` 时才成功）在验证码比对**之前**执行，只有递增成功才继续做常数时间摘要比较，避免"摘要不匹配 ⇒ 永远不计入尝试次数"的绕过。
- **TOTP 密钥加密**：`internal/auth/totp_crypto.go` 的 `TOTPCipher` 用标准库 `crypto/aes`/`crypto/cipher`（AES-256-GCM）加密 TOTP 密钥；密钥来自新增的、独立于 `SigningPrivateKey`/`SecretDigestPepper` 的必需配置字段 `AuthConfig.TOTPEncryptionKey`（环境变量 `AUTH_TOTP_ENCRYPTION_KEY`，32 字节原始 AES-256 密钥，unpadded base64url，与 `AUTH_JWT_SIGNING_PRIVATE_KEY` 同样的编码风格），是既有 auth 全有全无配置组的新成员（`internal/platform/config/config.go`）。明文密钥只存在于 `internal/auth` 包内部的函数调用栈中：`BeginTOTPEnrollment`/`ConfirmTOTPEnrollment`/`VerifyMFAChallenge` 内部解密后立即使用，从不记录日志、从不跨越 Service 边界返回。TOTP 校验用 `totp.ValidateCustom(code, secret, service.clock.Now(), ...)`（而非包级 `totp.Validate`，后者读真实墙钟）所以在注入 fake `Clock` 时是确定性的，可测。
- **OAuth 账户解析永不按邮箱匹配/合并**：`CompleteOAuthSignIn` 在 `(provider, provider_subject)` 未命中时总是创建一个新账号，其 `users.email` 是 `provider + uuid` 拼出的合成值，绝不直接使用 provider 报告的邮箱（provider 邮箱只写入 `oauth_accounts.email` 展示字段）——两个不同 `provider_subject` 报告相同邮箱因而永远解析到两个不同账号,由 `TestOAuthDifferentSubjectsSharingEmailNeverCollide` 覆盖。关联（link）是独立操作 `BeginOAuthLink`/`LinkOAuthAccount`：要求已认证会话且 access token 在 `oauthLinkReauthWindow`（5 分钟）内签发（`ErrReauthenticationRequired`，见 ADR-0008），并且授权 state 服务端记录的 `linking_user_id` 必须与回调时的认证用户完全一致，否则 `ErrOAuthStateInvalid`——`TestOAuthLinkRequiresMatchingAuthenticatedSession`、`TestOAuthLinkRequiresRecentReauthentication` 覆盖。MFA 强制策略（仅向前生效，不追溯撤销已签发 token）与 OAuth 关联策略的完整取舍记录在 [ADR-0008](../adr/0008-mfa-enforcement-and-oauth-account-linking-policy.md)。
- **WebAuthn**：`internal/auth/webauthn.go` 是唯一导入 `github.com/go-webauthn/webauthn` 的文件。`BeginWebAuthnRegistration`/`FinishWebAuthnRegistration` 在服务层（不只是 HTTP 中间件层）显式拒绝空 `userID`（`ErrWebAuthnUnauthenticated`），由 `TestWebAuthnRegistrationRejectedForUnauthenticatedCaller` 覆盖。`FinishWebAuthnAuthentication` 走 `webauthn.WebAuthn.ValidateDiscoverableLogin`，凭据归属通过 `DiscoverableUserHandler` 严格比对存储的 `user_handle` 与认证器上报的 `user_handle`；签名计数器不增长（clone 信号)通过检查返回 `Credential.Authenticator.CloneWarning`（库自身语义)以及 `UpdateWebAuthnCredentialSignCount` 的 `WHERE sign_count < $2` 条件双重拒绝。
- **契约**：全部新增操作仍在既有 `packages/contracts/features/auth/{models.tsp,routes.tsp,auth.tsp}` 内，未新建 `features/mfa`/`features/oauth` 模块：`POST /api/auth/otp/{request,verify}`、`POST /api/auth/mfa/totp/enroll/{begin,confirm}`、`POST /api/auth/mfa/challenge/verify`、`POST /api/auth/oauth/{provider}/{begin,callback,link/begin,link/callback}`、`GET /api/auth/oauth/accounts`、`POST /api/auth/webauthn/{registration,authentication}/{begin,finish}`。所有"完成登录"操作的成功响应是 `AccessTokenResponse | MFAChallengeResponse`（`MFAChallengeResponse` 显式声明 `statusCode: 202`，与 `AccessTokenResponse` 的隐式 200 区分，避免 ogen 不支持的同状态码 `anyOf`）。WebAuthn 的 `publicKey`/`credential` 字段用 TypeSpec `Record<unknown>` 声明为自由 JSON 对象（ogen 生成 `map[string]jx.Raw`），由 `internal/auth/handler.go` 的 `toRawMap`/`fromRawMap` helper 在这个自由对象和 `protocol.ParseCredential*ResponseBody` 所需的原始 JSON 字节之间转换。
- **配置**：`internal/platform/config.AuthConfig` 新增必需字段 `TOTPEncryptionKey`（`AUTH_TOTP_ENCRYPTION_KEY`），加入既有 auth 全有全无组；OAuth（`OAuthConfig.{Google,GitHub}`）与 WebAuthn（`WebAuthnConfig`）配置组在 A 阶段已经存在，本次未改变其形状，只是首次被消费：`apps/server/main.go` 的 `buildIdentityService` 现在接收完整 `config.Config`（而非仅 `AuthConfig`）以便同时读取 `cfg.OAuth`/`cfg.WebAuthn`，新增 `buildOAuthClients` 按 provider 装配 `auth.OAuthClient`。

## Integration checklist for later owners

- [ ] Run `pnpm generate` after adding or changing TypeSpec endpoint declarations; inspect and commit generated diffs instead of editing them.
- [ ] Add new Goose migrations only; pair data access changes with sqlc generation and tests.
- [ ] Use config values only in composition roots/adapters; do not log secret-bearing config fields.
- [ ] Preserve notification intent versus delivery attempt as separate domain concepts.
- [ ] Verify Stripe webhooks before changing entitlement state, and do not use Stripe as an authorization engine.
- [ ] Record exact commands and outcomes in this ledger before requesting integration.
